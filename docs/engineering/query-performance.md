# Производительность чтения журнала

Документ фиксирует baseline, измерения и решения по оптимизации read-путей Trades/Accounts. Он дополняет [analytics-performance.md](analytics-performance.md), который отвечает за фоновый аналитический отчёт.

## Методика

- Benchmark: `platform/database/src/query-benchmark.test.ts`, запускается в обычном `pnpm test`.
- Fixture: vault с 5 000 сделок (каждая десятая — с исполнением и двумя выходами) и 100 счетами; строки вставляются bulk-запросами внутри транзакций, чтобы измерять чтение, а не запись.
- Метрики: длительность операции, число подготовленных statement-ов через `platform/database/src/testing/query-counter.ts` (адаптеры готовят statement на каждый вызов, поэтому счётчик — стабильный прокси количества запросов) и удержанная память (retained size) при доступном `global.gc`.
- Абсолютное время зависит от загрузки раннера (в параллельном `pnpm check` значения выше), поэтому регрессионным gate являются количество запросов и удержанный payload, а время и heap — ориентиром.

## Baseline и результат

| Операция                               | Baseline (запросов / мс) | После (запросов / мс) |
| -------------------------------------- | ------------------------ | --------------------- |
| `listTrades` (5k, 10% executions)      | 502 / 30.5               | 3 / 27.2              |
| `listAccounts` (100 accounts)          | 501 / 10.6               | 5 / 6.2               |
| `getTradeById` (журнал 5k)             | — (использовался list)   | 3 / 0.2               |
| `readPage` limit 100 (журнал 5k)       | —                        | 6 / 4.2               |
| quick summary over 5k (полный список)  | —                        | 3 / ~36               |
| quick summary over 5k (streamed facts) | —                        | 1 / ~24               |

Потоковый summary измеряется на том же фикстуре: `SqliteTradeSummaryFactSource.iterate()` читает узкую проекцию одной prepared-инструкцией без exits/tags/notes, поэтому число запросов не зависит от размера журнала, а сам список сделок не материализуется. Точное сравнение длительностей зависит от загрузки раннера; регрессионные gates — количество statement-ов (3 → 1), удержанный payload и тест ленивости `platform/database/src/sqlite-trade-summary-fact-source.test.ts`.

## Память

Замер retained size встроен в тот же benchmark: `global.gc` включается через `test.execArgv` в `vitest.config.ts`, heap читается после сборки мусора до и после операции, поэтому дельта не включает промежуточные аллокации. На 5 000 сделках одного инструмента:

| Путь                                       | Удержанная память | Удержанный payload | Граница                   |
| ------------------------------------------ | ----------------- | ------------------ | ------------------------- |
| `listTrades` как результат                 | ~2.9 MiB          | ~2.88 МБ JSON      | O(сделки)                 |
| streamed summary                           | ~0                | ~182 байта         | O(уникальные инструменты) |
| снимок перепривязки (350 затронутых строк) | —                 | ~21.6 КБ           | O(переписанные строки)    |

`summarizeTradeFacts` держит только счётчики, один Decimal-итог и `Map` по уникальным инструментам (для best/worst); снимок перепривязки — массив затронутых строк, который растёт с их числом, но не с журналом. Абсолютные значения heap зависят от коллектора и остаются ориентиром; детерминированный gate — `expect(summaryPayloadBytes * 100).toBeLessThan(fullListPayloadBytes)`, число statement-ов и постоянное число запросов на снимок/inverse в `platform/database/src/sqlite-trade-preferences.test.ts`.

Регрессионные тесты с точными границами: `platform/database/src/query-counts.test.ts` проверяет, что количество запросов не зависит от размера журнала (12 → 62 сделки, 5 → 40 счетов) и что точечный lookup ограничен тремя statement-ами.

## Optimization ledger

| Кандидат                                              | Решение и причина                                                                                                                                                                                                                                                                                 |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Batch-загрузка `trade_exits` вместо запроса на сделку | Keep. 502 → 3 запроса, чанки по 500 id, порядок `exit_order` сохранён.                                                                                                                                                                                                                            |
| `getTradeById` вместо `listTrades().find(...)`        | Keep. Update-путь и IPC-снимки больше не читают весь журнал; 0.2 мс на 5k.                                                                                                                                                                                                                        |
| Grouped read model для `listAccounts`                 | Keep. 501 → 5 запросов; Decimal-точность сохранена (суммы считаются в памяти из строк, без `SUM(... AS REAL)`).                                                                                                                                                                                   |
| Точные точечные lookup-ы счёта/актива/тега            | Keep. Используются в IPC update/delete вместо полного списка.                                                                                                                                                                                                                                     |
| Ресурсная инвалидация renderer                        | Keep. Коммит-событие обновляет только затронутые группы; коалесцинг и single-flight в `RefreshScheduler`; мутация больше не дублирует refresh.                                                                                                                                                    |
| Fallback-refresh после мутации                        | Keep. Таймер 250 мс срабатывает только если событие не пришло (потерянное событие не оставляет UI устаревшим).                                                                                                                                                                                    |
| Streaming fact source для quick summary               | Keep. `analytics.summary` проходит одним `iterate()` по узкой проекции (1 statement) и не грузит exits/tags/notes; паритет с полным чтением закреплён `platform/database/src/sqlite-trade-summary-fact-source.test.ts`. Число запросов не зависит от журнала, память — O(уникальные инструменты). |
| Кэш списков/React Query                               | Reject. Нет измеренного узкого места после удаления N+1; добавит инвалидационную сложность.                                                                                                                                                                                                       |
| Bounded keyset-страницы журнала (`readPage`)          | Keep. 4.2 мс и 6 statement-ов на 100 строк журнала 5k (добавлен batch-подсчёт выходов для колонки «Выходы»); table DTO не загружает executions/exit-rows и содержимое заметок, полная сделка читается точечно при открытии редактора; ADR-0013/0016.                                              |

## Правила

- Новый read-путь списка обязан иметь регрессионный тест на количество запросов, не зависящее от числа строк.
- Списки не выполняют запрос «на элемент»; связанные строки читаются batch-запросом с чанками.
- Финансовые агрегаты считаются точными значениями; SQLite `REAL` для денег запрещён.
- Мутации не запускают немедленный полный refresh: источник истины — коммит-событие, fallback покрывает только потерянное событие.
- Смена поколения vault всегда выполняет полный refresh.
