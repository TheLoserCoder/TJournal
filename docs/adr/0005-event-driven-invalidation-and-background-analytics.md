# ADR-0005: Событийная инвалидация и фоновая аналитика

## Status

Accepted.

## Context

Статистика зависит от сделок, выходов сделки, профилей инструментов и настроек классификации. Если обновление одной таблицы вручную вызывает пересчёт в нескольких местах, со временем появляются забытые ветки и устаревшие карточки. Полный синхронный пересчёт в main process также может задерживать сохранение при большом журнале.

## Decision

SQLite остаётся единственным источником истины. Миграция `005-data-revisions` добавляет монотонные ревизии для аналитически значимых ресурсов и SQLite-триггеры на insert/update/delete. После каждой успешной транзакции main process через `CommittedChangeCoordinator` сравнивает ревизии, публикует typed `data:changed` event и передаёт renderer только список затронутых ресурсов, ревизии и поколение vault.

Пересчёт статистики выполняется одним `Piscina` worker с read-only подключением к тому же SQLite-файлу. В очереди находится максимум одна ожидающая задача; новый запрос отменяет прежний. Worker повторно читает сделки и настройки, применяет общую Decimal-логику `@tjournal/analytics` и возвращает ревизии снимка. Renderer обновляет ViewModel асинхронно и не блокирует запись.

Границы остаются явными: domain/application не знают о worker и Electron; worker-клиент и публикация событий создаются только в desktop composition root; renderer получает изменения только через preload gateway.

## Consequences

- Любая текущая операция, которая меняет таблицы, автоматически инвалидирует зависимую статистику, включая Undo/Redo и массовое удаление.
- При серии изменений промежуточные расчёты отменяются, поэтому UI стремится к последнему согласованному состоянию, а не создаёт очередь тяжёлых задач.
- Согласованность статистики становится eventual: во время короткого пересчёта показывается предыдущий результат и индикатор обновления.
- Read-only worker не может изменить vault; закрытие приложения уничтожает worker до закрытия основного соединения.
- Новая аналитическая зависимость должна зарегистрировать ресурс и триггер в миграции, добавить событие в coordinator и тест на инвалидацию.

## Alternatives considered

- Синхронно считать статистику в IPC handler — проще, но блокирует main process.
- Полностью переносить SQLite в worker — уменьшает работу main, но существенно усложняет транзакции, Undo/Redo и жизненный цикл vault; это отдельное решение при подтверждённом профилированием узком месте.
- Использовать только React-зависимости — не ловит изменения, сделанные через другие main-process операции и не даёт единой ревизии данных.
